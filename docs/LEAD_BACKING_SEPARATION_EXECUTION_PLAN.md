# 主唱/伴唱高质量分离实施方案（可执行版）

## 1. 目标与范围

### 1.1 目标

- 在现有“人声/非人声分离”基础上，实现“主唱/伴唱”高质量分离。
- 覆盖两条链路：
  - 本地音高解析-实时分析（近实时，允许可控延迟）
  - 本地音高解析-一次性绘制（离线高质量）
- 提供可操作 UI：
  - 是否包含伴唱
  - 伴唱人数（用户输入或自动建议）
  - 主唱/伴唱预览试听后确认

### 1.2 非目标（本期不承诺）

- 在所有歌曲类型上实现完全无串音分离。
- 在纯 CPU、超低算力设备上同时达到“极低延迟 + 最高分离质量”。

## 3. 技术路线（推荐）

## 3.1 两阶段分离架构

- 阶段 A：音乐分离（已有）
  - 混合音频 -> vocal stem + accompaniment stem
  - 引擎优先 Demucs（质量优先）
- 阶段 B：人声内部分离（新增）
  - vocal stem -> 多人声轨（主唱候选 + 伴唱候选）
  - 对候选做音色嵌入与聚类，确定主唱轨与伴唱轨

### 3.2 主唱识别策略

- 优先推荐：主唱模板锁定
  - 让用户在开始前录制/选择 3-8 秒“主唱参考段”。
  - 从参考段提取 speaker embedding，推理时按相似度匹配主唱轨。
- 无模板时：
  - 自动规则 + 聚类中心：能量连续性、音区连续性、嵌入稳定性联合打分。

### 3.3 实时与离线分开优化

- 近实时模式：
  - 小窗口分块推理（例如 chunk 0.5-1.0s，hop 0.1-0.25s）
  - 目标首帧延迟 <= 1200ms，稳定后更新间隔 <= 200ms
- 一次性模式：
  - 全曲高质量分离与二次平滑
  - 目标：主唱音高曲线碎点率显著低于实时模式

## 4. 开源库选型（高质量优先）

### 4.1 必选（建议）

- demucs（已有，可继续主用）
- torch / torchaudio（模型推理、重采样、IO）
- ffmpeg-python 或直接 ffmpeg CLI（格式与采样率统一）
- librosa（特征与后处理）

### 4.2 人声内部分离（二选一起步）

- 方案 B1（工程风险较低，先落地）：
  - pyannote.audio（分段 + 聚类 + embedding）
  - speechbrain（embedding 备选）
- 方案 B2（质量上限更高，调参成本更大）：
  - asteroid（Conv-TasNet/DPRNN 类语音分离模型）
  - 再叠加 embedding 做主唱归属

### 4.3 可选增强

- onnxruntime-gpu（模型导出后推理提速）
- noisereduce（轻量降噪，仅在低信噪比场景触发）

## 6. UI 与交互流程（可直接做）

### 6.1 录音/分析前设置

- 弹窗字段：
  - 是否包含伴唱：是/否
  - 伴唱人数：0-4
  - 主唱识别方式：模板锁定/自动
  - 质量模式：标准/高质量
  - 设备能力提示：CPU/GPU 状态

### 6.2 预览试听

- 生成主唱轨与伴唱轨后，提供 10-20 秒试听区间：
  - 主唱独听
  - 伴唱独听
  - 混听 A/B
- 用户确认后才进入正式绘制。

### 6.3 绘制策略

- 实时绘制：默认只绘制主唱主线，伴唱可选叠加。
- 一次性绘制：支持多轨分色，并可一键切换“主唱优先视图”。

## 7. 参数基线（第一版建议）

### 7.1 分块参数（实时）

- sample_rate: 44100
- chunk_sec: 0.75
- hop_sec: 0.20
- overlap: 73%
- warmup_chunks: 2

### 7.2 主唱归属阈值

- cosine_sim(main_ref, track_emb) >= 0.58：判为主唱候选
- 0.48-0.58：进入“待确认区”并结合连续性评分
- < 0.48：默认为伴唱

### 7.3 连续性约束（降低抖动）

- 轨道切换惩罚：前后 500ms 内切换加罚
- 最短保持时长：主唱轨至少保持 700ms
- 音高跳变限幅：与现有主唱优先策略联动

## 8. 质量指标与验收标准

### 8.1 客观指标

- 分离质量：
  - SDR/SIR/SAR（有基准集时）
- 业务指标：
  - 主唱轨碎点率（points_per_sec 中异常孤立点比例）
  - 主唱轨连续率（连续帧占比）
  - 伴唱误吸附率（伴唱被误归主唱比例）

### 8.2 时延与性能指标

- GPU 模式：
  - 首次可视化延迟 <= 1.2s
  - 稳态帧处理耗时 P95 <= 140ms
- CPU 模式：
  - 首次可视化延迟 <= 2.0s
  - 稳态帧处理耗时 P95 <= 260ms

### 8.3 验收门槛（建议）

- 对比当前版本：
  - 主唱碎点率下降 >= 30%
  - 嘈杂伴唱场景主唱连续率提升 >= 20%
  - UI 操作成功率 >= 99%

## 11. 风险与规避

- 风险 1：多人和声密集段主唱归属抖动
  - 规避：模板锁定 + 连续性惩罚 + 最短保持时长
- 风险 2：CPU 设备卡顿
  - 规避：自动切换轻量模型/增大 hop/只主唱绘制
- 风险 3：模型下载与环境差异
  - 规避：本地缓存目录 + 启动前预检查 + 明确错误提示

## 12. 你可以直接使用的决策建议

- 若你当前优先“高质量可上线”：
  - 先选 B1（pyannote.audio 路线）做 stage2。
  - 实时先做近实时，不追求极低延迟。
- 若你当前优先“演示效果最快”：
  - 先做主唱模板锁定 + 离线高质量，实时只上主唱轨。
